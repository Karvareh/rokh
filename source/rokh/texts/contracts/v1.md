# Rokh v1: the contract

Status: the contract that version 1 is built to. Where the code differs from a
clause, the documents say so.

Precedence: the treatise and the ledger without consensus (`رساله.md`,
`without-consensus.md`) > this contract > every older document and the existing code. Where an older document disagrees (content outside the
carrier, clear anchor, `seat.json`, root-only disclosure, Unix-only doors, the 0.9
formats and protocols), this contract replaces it.

Words: MUST, MUST NOT, MAY are binding. "Red" means: not proven, reported as failed with
evidence. No acceptance clause is reworded to make it pass.

---

## 0. Invariants of the core

C1. Core packages are `frame`, `event`, `ledger`, `carrier`, `vessel`, `key`, `lineage`.
    They import the Go standard library only, never `os`, `path/filepath`, `time`,
    `syscall`, `os/exec`, `os/user`, `os/signal`, `net`, `unsafe`, `runtime`, and carry
    no build tag and no per-OS file. Files, locks, clocks, sockets and processes reach
    the core only through injected interfaces. Their implementations are host adapters
    and live outside the core (section 2.9). A test holds this line.
C2. The core never reads a clock, never sleeps, never takes a lock itself, and never
    relies on a permission bit, an owner id, a symlink flag, an atomic rename, a
    directory flush or a file name's case.
C3. Zero external modules, `CGO_ENABLED=0`, no home-made primitive. Primitives:
    SHA-256, HMAC-SHA256, HKDF-SHA256, PBKDF2-HMAC-SHA256, AES-256-GCM, Ed25519, X25519.
C4. v1 writes and reads one event generation, RKH3 (section 3.4). The head of an event
    is one byte string that is signed, hashed and stored; the body is a second byte
    string that the head names by hash. Nothing signed is rewritten.
C5. Every source of randomness in `vessel`, `key` and `lineage` is an injected
    `io.Reader`. With the same inputs and the same random stream, the bytes on the medium
    are identical on every platform. That is the format test of goal 8.4.
C6. No event is created by itself. Union, recovery, rebuild of views and backfill of
    envelopes create no event.
C7. Every read is bounded and every slab is verified before one byte of it is consumed.

Four invariants fail closed. Each is an acceptance check (section 9, S1 to S4).

C8. Unauthenticated ancestry never authorizes a write. A grant, revoke, keyring or
    write verdict rests only on signed bytes: the event itself, its authority chain in
    full, and the hash-linked signed head of every ancestor. Record headers, indexes
    and hints prove nothing. What cannot be proven is `pending` and the write is
    refused.
C9. No stale writer overwrites a committed generation. A commit writes only while the
    injected owner still holds the vessel, and never into a slab that is live in one of
    the last R generations. Ownership that cannot be held until release or death is
    not offered for writing; the vessel then opens for reading only.
C10. Chunks bind their coordinates. Index, count, total size and length are
    authenticated with every chunk. Content is served only after the whole of it has
    hashed to its id.
C11. Operating-system and file adapters stay outside the portable core (C1).

## 1. Vessel parameters and names (goal 6.4)

| parameter | value |
|---|---|
| format name | `rokh.vessel/1`, magic `RKV1` |
| footprint | one directory, `rokh`, inside the carrier folder. `Footprint() = ["rokh"]` |
| name alphabet | `a-z 0-9`, one dot, written lowercase; readers fold ASCII case |
| name shape | 8.3: base 1..8, extension exactly `rkh`. No leading dot, no space, no Unicode |
| head files | `rokh/head0.rkh` .. `rokh/head3.rkh` (HeadSlots = 4), each 65,536 bytes |
| slab files | `rokh/<ddd>/<nnnnnnnn>.rkh`; `nnnnnnnn` = slab index, 8 hex; `ddd` = index>>10, 3 hex |
| writer's lock | the host's kernel lock on `rokh/head0.rkh`; nothing is created or written for it |
| slab size S | 2^k bytes, k in 18..26. Default k = 20 (1 MiB) |
| slab count N | 16 .. 4,194,304 (2^22). Default 64 |
| per directory | at most 1,024 slab files; at most 4,096 slab directories |
| longest path | `rokh/fff/003fffff.rkh`, 21 bytes |
| retention R | 3 generations |
| key slots | 32 cells of 256 bytes in every head file |
| growth | `fixed` (default) or `auto(step, max)` |

Why these fit: FAT32 allows 4 GiB − 1 per file and 65,534 entries per directory; a
lowercase 8.3 name costs at most two entries. exFAT and cloud folders are case
insensitive and some refuse or hide dot-names, `: * ? " < > |`, trailing dots and device
names (`con`, `nul`, `aux`, `prn`, `com1`..). None of these can occur in the grammar above.

Foreign entries (`desktop.ini`, `.DS_Store`, `Thumbs.db`, conflict copies, anything outside
the grammar) are ignored, never read as data, never deleted by Rokh.

At every instant, also in the middle of a write, the vessel is exactly `N + 4` files of
`N × S + 4 × 65,536` bytes. The format has no temporary file, no lock file and no
rename. The file set and the lengths change only by `grow`, `shrink`, or an `auto` growth
step. Logical length and allocated blocks are measured separately (A1). What a file
system adds of its own (directory entries, journals, snapshots, copy-on-write) is outside
this number (U1).

## 2. Vessel: inventory, commit point, recovery (goal 6.3)

### 2.1 Keys of the storage layer

`VK` is 32 random bytes, made per vessel (each seed has its own).
`SLK = HKDF-Expand(VK, "rokh/vessel/1/slabs")`, `HDK = HKDF-Expand(VK, "rokh/vessel/1/heads")`,
`PTK = HKDF-Expand(VK, "rokh/vessel/1/shared")`.
Every key of the rokh, of any right, holds VK of the vessel it opens.

### 2.2 Slab

```
slab file  := salt(32) || ciphertext(S-48) || tag(16)
key        := HKDF-SHA256(secret=SLK, salt=salt, info="rokh/vessel/1/slab")
nonce      := 12 zero bytes            (the key is single-use)
aad        := vessel_id(32) || index(u32 BE)
plaintext  := kind(1) || zero(3) || used(u32 BE) || body(used) || zero padding
kind       := 0x01 inventory segment | 0x02 record pack
```

A free slab is S bytes of randomness. A slab is never partly written: a writer produces
all S bytes and flushes the file.

### 2.3 Head file

```
off 0      "RKV1"
off 4      kdf id (0x01 = PBKDF2-HMAC-SHA256), 3 zero bytes
off 8      iterations (u32 BE), 1..10,000,000, default 600,000
off 12     salt(32); salt and iterations are one per rokh, inherited by every seed
off 44     20 zero bytes
off 64     32 slot cells × 256 bytes (section 4.6); an empty cell is randomness
off 8256   root box: salt(32) || ciphertext || tag(16), to the end of the file
             key = HKDF-SHA256(HDK, salt, "rokh/vessel/1/head"); nonce zero
             aad = bytes 0..63 || head file number(1)
             plaintext = len(u32) || root record || zero padding
```

Root record, canonical TLV (the `frame.EncodeFields` codec):

| tag | field | value |
|---|---|---|
| 0x0001 | format | `rokh.vessel/1` |
| 0x0002 | generation | u64, starts at 1, +1 per commit |
| 0x0003 | anchor | 32 bytes, the genesis id |
| 0x0004 | vessel | 32 random bytes, this physical vessel |
| 0x0005 | seed | 32 bytes, the seed id; absent on the root vessel |
| 0x0006 | slab | u8 k and u32 N |
| 0x0007 | growth | mode(1), step(u32), max(u32) |
| 0x0008 | segments | list of `index(u32) || digest(32)`, one per inventory segment, in order |
| 0x0009 | token | 16 random bytes, the commit's own name |
| 0x000A | scopes | address prefixes this vessel holds; absent means whole |

`Create` writes generation 1 into `head1.rkh` and fills the other three head files with
randomness. A head file that does not open is not an error; it is not a generation.

Visible without a key: that this is a rokh vessel of format 1, the KDF cost and salt, S,
N, and file times. Not visible: anchor, names, addresses, the count or size of any item,
the number of keys.

### 2.4 Inventory

Segment j covers slab indices `[4096·j, 4096·(j+1))`. It is a slab of kind 0x01 whose body
is 4,096 entries of 46 bytes:

```
entry := state(1) || kind(1) || gen(u64) || used(u32) || digest(32)
state := 0x00 never used | 0x01 live | 0x02 free
gen   := generation that wrote it (live) or freed it (free)
digest:= SHA-256 of the whole slab file (live only)
```

### 2.5 Records

A pack slab's body is a run of records:

```
record := type(1) || len(u32 BE) || body
0x01 event    id(32) || hlen(u16) || head(hlen) || envelope     head: the signed RKH3 head (3.4); the envelope seals the body
0x02 content  id(32) || chunk(u32) || chunks(u32) || size(u64) || envelope
0x03 pointer  space(1) || name(32) || envelope        mutable, the latest commit wins
0x04 object   space(1) || name(32) || chunk(u32) || chunks(u32) || size(u64) || envelope   immutable
```

One chunk of plaintext is at most `S − 4096` bytes; every chunk but the last is exactly
that long. Spaces: 0x01 ledger references (branches), 0x10..0x1F the home (objects,
pointers, journal). The heads of all events are the **lineage index**. A head proves
itself: it hashes to the id that names it and it carries its author's signature. Every
other header field is a locator and proves nothing (C8).

### 2.6 Commit point

One recording is one commit. A commit that produces generation n:

1. asks the injected owner whether it still holds the vessel, reads the head files,
   takes the highest valid generation n−1;
2. writes every new or rewritten slab into slabs that are `never used`, or `free` with
   `n − gen ≥ R`, chosen with the injected randomness; asks the owner before each file
   and flushes each file;
3. writes the changed inventory segments the same way; flushes;
4. asks the owner again and re-reads the head files; if the owner no longer holds, or
   the highest valid generation is no longer n−1, nothing was committed: `not-recorded`,
   code `turn_lost`;
5. writes head file `n mod 4` whole, flushes it;
6. re-reads that file and compares the token. Equal: `recorded`. Different: `not-recorded`.
   Unreadable: `unknown`.

The host gives the ownership back; the core does not.

Before step 5 nothing, after it everything. A slab that is live in any of the last R
generations is never written. When the free slabs do not suffice, `fixed` mode answers
`vessel_full` before step 2 writes a byte and `auto` mode grows first.

### 2.7 Opening and recovery

Opening reads the four head files, unlocks VK through a slot, opens each root box, and
takes the highest generation g for which every inventory segment and every slab with
`gen > g − R` matches its digest. If g is not the highest generation seen, the report says
so: `fell_back{from, to, why}`. Older slabs are verified when first read. A digest or tag
mismatch makes the reader refresh the head once, then fail with `vessel_corrupt`; nothing
from that slab is returned.

Recovery writes nothing by itself. `Report` lists: generation opened, fallbacks, torn head
files, slab files missing or of the wrong size, slab files beyond N.

### 2.8 Grow, shrink, automatic growth

- `grow --to SIZE`: creates slab files N..N'−1 filled with randomness, then commits N'.
- `shrink --to SIZE`: refused unless the live slabs fit. Moves live slabs above the new
  count below it by ordinary commits, commits N', and removes the tail files only after R
  further generations or an explicit `--finish`.
- Both name a target, never a delta, so repeating either changes nothing.
- A crash leaves files beyond N: they are ignored and reported.

### 2.9 Ownership and host adapters

The core holds no lock and no clock. A writer hands it an `Owner` (2.10) that the host
made. Adapters are packages outside the core:

| adapter | package | darwin | linux | android | windows |
|---|---|---|---|---|---|
| files, `Medium` | `medium` | portable `os` calls | same code | same code | same code |
| writer's lock, `Owner` | `turn` | `flock` | `flock` | `flock` | byte-range lock beyond the end of the file |
| booth transports | `transport` | Unix socket, 127.0.0.1, pipe, inherited descriptor | same | same | 127.0.0.1, pipe, Unix socket |
| process control, enclosure, terminal | the booths and the commands | as built | as built | not built | not built |

- The lock is the kernel's: exclusive, held until release or until the holder dies. It
  is never a timer and it is never taken from a living holder. A paused holder still
  holds. Readers may share it.
- `Holds()` answers from the live lock handle.
- A host that has no such lock offers no `Owner`. Vessels then open for reading only,
  code `turn_unavailable`.
- An adapter compiled for a target and never run there is red for that target.
  Cross-compilation is not a run.

## 3. Object and envelope; restricted opening (goal 6.1)

### 3.1 Envelope

```
envelope := ver(1)=0x01 || suite(1) || ...
suite 0x01 (readers):
   n(u16) || eph(32) || n × rcpt || nonce(12) || ciphertext || tag(16)
   rcpt    := kid(8) || wnonce(12) || wrapped(48)
   kid     := first 8 bytes of SHA-256("rokh/kid/1" || reader_pub)
   CK      := 32 random bytes, one per envelope
   body    := AES-256-GCM(CK, nonce, plain, aad = "rokh/env/1" || type(1) || id(32) || at)
   at      := empty for an event and for a pointer; for a chunk of content or of an object:
              chunk(u32) || chunks(u32) || size(u64) || length(u32)
   wk      := HKDF-SHA256(X25519(eph_priv, reader_pub), nil, "rokh/env/1/wrap" || eph || reader_pub)
   wrapped := AES-256-GCM(wk, wnonce, CK, aad = id || at)
suite 0x02 (shared key):
   kid(8) || salt(32) || ciphertext || tag(16)
   key := HKDF-SHA256(K, salt, "rokh/env/1/shared"); nonce zero; aad as above
```

n is 1..32. An unknown `ver` or `suite` is unread, not invalid: the reader says which
generation it does not hold.

### 3.2 Rules

E1. For an event the envelope seals the body. After opening, SHA-256 of the body must
    equal the `body` field of the signed head whose hash is the id (3.4). For content
    `id` is SHA-256 of the whole content. A mismatch is a forgery: the record is refused
    and reported, and nothing of it is shown.
E2. One id may sit in several envelopes. All that open must open to the same bytes.
E3. Every suite-0x01 envelope MUST name every live generation of the owner's reader. A
    record whose envelope lacks it is refused at commit, at union and at opening.
E4. Readers of an event written at address A, as judged at the event's parents:
    the owner; every live key generation whose `reads` cover A; the system reader if A is
    `rokh` or A lies under a read-open address.
E5. Content takes the readers of the event that describes it. Content lives inside the
    vessel. The machine library outside the carrier is no longer written.
E6. Secrets (ssh keys, passwords, logins) are content with their own envelope: an address
    of their own, read by the keys whose scope names it, nothing else.
E7. Branch references are pointers of space 0x01 under suite 0x02 with `K = PTK`.
E8. Content and objects are assembled in bounded memory, one chunk at a time. `chunks`
    and the length of every chunk follow from `size`; a chunk whose coordinates disagree
    with that does not open. Two chunks with the same coordinates and different
    plaintext refuse the whole content, code `content_conflict`. A missing chunk refuses
    it, code `content_incomplete`. Sealing proves no author, so nothing is served until
    every chunk has opened and the whole has hashed to the id.

### 3.3 Restricted opening and its necessary lineage

A session opened with a key holds a view: the events and content it can open.

The **necessary lineage** of a view is exactly:
1. the signed head of every ancestor of what it opens (3.4), and no body;
2. every system event in full (genesis, grant, revoke, merge, keyring, seed). Their
   bodies are sealed to the system reader, whose private half every key holds.

A head counts as lineage only when it hashes to the id by which a verified child or a
verified head names it, and its signature verifies under its own author field.

Verdicts in a view:

| verdict | meaning |
|---|---|
| `full` | the ledger's own judgement: the head and the body of every ancestor verified |
| `lineage` | the event's head, body and signature verified; every ancestor's head verified by hash link and signature; every grant, revoke and keyring event in its causal past judged in full; its own grant live, unrevoked in that past, made to its author, covering its address and verb. Not judged: whether an ancestor whose body cannot be opened obeyed its own grant |
| `pending` | a head is missing or does not hash to its name, or a needed system event is absent. Nothing is authorized (C8) |

A restricted view reports `lineage`, never `full`, on every surface. A booth records a
write on `lineage` only when its session key can do no better, and says so in the answer.
The owner's `full` judgement is final when it is made.

What every key sees: the heads (author, grant named, parents) and the system layer
(keys' names and public halves, scopes, rights, seeds). What it never sees outside its
view: an address, a verb, a payload, a content byte.

### 3.4 The event, generation RKH3

```
event := head || body
head  := "RKH3" || kind(1)=0x01 || hlen(u32 BE) || fields(hlen) || sig(64)
sig   := Ed25519(author, every byte of the head before it)
id    := SHA-256(head)
body  := fields
```

| where | tag | field | value |
|---|---|---|---|
| head | 0x0001 | carrier | 32, the anchor; absent only in genesis |
| head | 0x0002 | author | 32, Ed25519 |
| head | 0x0003 | authority | 32, id of a grant; absent when the author is the root |
| head | 0x0004 | parents | 32·n, ascending, 1 to 16; absent only in genesis |
| head | 0x0009 | fresh | 4 random bytes |
| head | 0x000A | body | 32, SHA-256 of the body bytes |
| head | 0x000B | system | 0x01 when the address is `rokh`; otherwise absent |
| body | 0x0005 | address | UTF-8 |
| body | 0x0006 | verb | UTF-8 |
| body | 0x0007 | payload | up to 4,096 bytes; absent when empty |
| body | 0x0008 | attest | attestations; absent when empty |
| body | 0x000C | salt | 32 random bytes, always present, so that the body's hash hides the body |

Fields are canonical TLV, the `frame.EncodeFields` codec: ascending tags, no duplicate,
no empty value, one spelling. The head is at most 1,024 bytes and the body at most 8 KiB.
An event without its body is a **head only**: it proves lineage and authorship and
nothing of content. The rules for addresses, verbs, limits, freshness and authority in
the causal past are the ledger's own and do not change. A reader that meets another magic
says which generation it does not hold.

## 4. `rokh.keyring`, `rokh.seed`, the open address (goal 6.2)

### 4.1 Reserved verbs

The known reserved verbs are six: `rokh.genesis`, `rokh.grant`, `rokh.revoke`,
`rokh.merge`, `rokh.keyring`, `rokh.seed`. All sit at address `rokh`. All events have one
construct, RKH3; a system event differs only by its address and carries the mark `system`
on every surface, in the same line format.

### 4.2 `rokh.keyring` payload (canonical TLV)

| tag | field | value |
|---|---|---|
| 0x0001 | op | 0x01 add, 0x02 revoke |
| 0x0002 | key | 32 bytes, the key's id, stable across generations; 32 zero bytes is the owner |
| 0x0003 | gen | u32, from 1 |
| 0x0004 | name | one address component, 1..64 bytes |
| 0x0005 | reader | 32 bytes X25519, always present |
| 0x0006 | signer | 32 bytes Ed25519; absent means the key cannot write |
| 0x0007 | reads | list of `len(1) || prefix`; absent means it reads nothing; one empty prefix means everything |
| 0x0008 | slot | 160 bytes, the key's wrapped private half (4.6); absent for the owner |
| 0x0009 | heir | 92 bytes, the previous generation's reader private half sealed to this reader |
| 0x000A | target | revoke only: id of the `add` being taken back |
| 0x000B | system | 92 bytes: the system reader's private half sealed to this reader |

### 4.3 Authority, generation, future revocation

K1. `add` and `revoke` are accepted from the root only. A key may also revoke its own
    generation. Delegated keyring writing is not in v1.
K2. Writing is still `rokh.grant` to the key's `signer`; taking it back is `rokh.revoke`.
    Reading is `reads`. The two are independent and each may be empty: read-only,
    write-only, no right.
K3. A generation is never edited. Changing a name, a scope or a key pair is `add` of
    gen+1 and `revoke` of the old one.
K4. Revocation closes the future. From the first event that has the revoke in its causal
    past, writers stop sealing to that generation. What was sealed to it stays open to it.
K5. Rotation of a shared (group) key is K3 with new key pairs. `heir` lets the new
    generation open what the old one could. The removed holder keeps the old half only.

### 4.4 Concurrent changes

State at a point P is a fold of P's causal past and nothing else:

```
live(P)   = { add events in past(P) } \ { targets of revoke events in past(P) }
readers(A, P) = owner generations ∪ { g in live(P) : g.reads covers A }
```

Both sets only grow, so union of two seeds commutes and a revoked generation never comes
back. Concurrent `add`s for one key leave several live generations; all are in force, and
every surface marks the key `concurrent` until the owner revokes all but one. A revoke
concurrent with an add of the same key id does not touch the add it never saw.

### 4.5 The open address

A grant MAY carry tag `0x0005 open = 0x01` and then MUST NOT carry a subject or
`CanDelegate`. An event by any key that names an open grant as its authority is accepted
when the grant is live in its causal past, covers its address and verb, and the verb is
not reserved. Nowhere else is a key without a grant accepted. An open grant with
`0x0006 read = 0x01` makes its scope read-open: events there are sealed to the system
reader too. Only the root writes an open grant.

### 4.6 Slots and passphrases

```
kk    := PBKDF2-HMAC-SHA256(passphrase, salt, iterations, 32)
cell  := blob(160) || vkseal(92) || random(4)
blob  := nonce(12) || AES-256-GCM(HKDF(kk,nil,"rokh/1/slot"), nonce, p, aad="rokh/1/slot") || tag(16)
p     := key(32) || gen(u32) || flags(u32) || signer_seed(32) || reader_priv(32) || zero(28)
vkseal:= VK sealed to reader_pub: eph(32) || nonce(12) || ct(32) || tag(16), info "rokh/1/vk"
```

A passphrase opens a vessel by trying every cell. The first passphrase is the owner's:
its slot holds the root signing seed (or zeros in cold custody) and the owner's reader,
and it is never placed in an event. Any session that holds VK installs the cell of a key
it learns from a keyring event. The owner's passphrase has no recovery and gets none.
Changing a passphrase rewrites the cell and commits four generations, so that no head
file of this vessel keeps the old cell. Copies made earlier keep it; that is U6.

### 4.7 `rokh.seed` payload

| tag | field | value |
|---|---|---|
| 0x0001 | op | 0x01 give, 0x02 take |
| 0x0002 | seed | 32 random bytes, the seed's id |
| 0x0003 | key | 32 bytes, id of the keyring key made for the seed |
| 0x0004 | scopes | list of prefixes; absent means whole |
| 0x0005 | source | seed id of the giving vessel; absent means the root vessel |
| 0x0006 | give | take only: id of the give |
| 0x0007 | vessel | take only: the new vessel's id |

S1. `give` is accepted from the root only. Its scopes MUST lie inside the giver's own
    vessel scopes. `take` is accepted only from the signer of the key the give names, with
    the give in its causal past, under a live grant.
S2. `rokh seed SRC DST` records, in one commit on SRC: keyring `add` for the seed's key,
    one `rokh.grant` per scope, and `give`. It creates DST as a new vessel with its own
    VK, the inherited salt, the same anchor; copies genesis, every system event, the
    signed head of every ancestor, the events and content in scope; and records `take`
    on DST.
S3. A sliced seed holds its scopes and the necessary lineage of 3.3, nothing else.
S4. No folder becomes a rokh except by `init` (the root) or by `seed`.
S5. Repeating `seed` for a DST that already took that give changes nothing.

### 4.8 Reconcile

R1. Same anchor only. A different anchor is refused and no union is offered.
R2. Reconcile is union of records both ways, inside each side's scopes, then each side
    installs slots and rebuilds its keyring from events. It records no event.
    `reconcile --merge` and the sentence `reconcile` additionally record one `rokh.merge`.
R3. The result is a function of the two sets. Order and repetition change nothing.
R4. A session transfers only what it can judge: `full` with the owner's key, `lineage`
    with any other, never `pending`. Equality of everything needs a key that reads
    everything.
R5. The answer names both halves: `{local, remote}` each `recorded | not-recorded |
    unknown`. Anything but two `recorded` is a failure with exit code 3 (or 4 when
    unknown). The first half is never reported as the whole.
R6. Two seeds that meet through a booth or the command line reconcile without being
    asked; the command stays.
R7. After reconcile both sides list the same concurrent keys and the same heads.

## 5. Booth messages (goal 6.5)

Protocol name `rokh.booth/1`. The daemon and the gate stay: they are the two booths of
Rokh, above the core, rebuilt on this one protocol (axiom 32, goal 4.65 and 7.48). The
daemon is the booth of a carrier. The gate is the booth of a home: it identifies each
program, holds it to its view and starts it. The 0.9 protocol names, message shapes and
tests are not requirements.

B1. A message is one UTF-8 JSON object on one line, at most 8 MiB. Ids and keys are
    lowercase hex, other bytes base64, passed byte for byte. The protocol needs an
    ordered byte stream and nothing else: Unix socket, local TCP, pipe, socket pair,
    standard input and output. Listeners and dialers are host adapters in package
    `transport`, outside the core and outside `booth` (2.9).
B2. Request `{"v":"rokh.booth/1","id":"…","op":"…", …}`. Answer carries the same `id`,
    `ok`, and on failure `code` and `error`; every recording answer carries `record`.
B3. A session begins with `hello` and is bound to one key before anything else is
    answered. Nothing about the transport is an identity: no path, no port, no process id.

| op | purpose |
|---|---|
| `hello` | offers versions, `auth` (`key` or `credential`) and, for `key`, the key id; answers a 32-byte `challenge`, and for a key without signer the same challenge `sealed` to its reader |
| `prove` | `key`: Ed25519 signature over `"rokh.booth/1" \|\| challenge \|\| anchor`; a key without signer returns the challenge opened from a seal to its reader. `credential`: the booth's own token |
| `whoami` | key id, name, generation, reads, writes, open addresses, `judged` |
| `view` | the three layers of section 6 inside this key's view |
| `seed` | anchor, vessel id, seed id, scopes, generation, size, free |
| `status` `log` `wait` `get` `attempt` `receipts` `capabilities` | reading the ledger, filtered to the view; each event carries `system` and `judged` |
| `append` `write` `intent` `outcome` `bind` `bound` | recording and the receipt custom, under the session key; typed answers `recorded`, `not-recorded`, `unknown`; preconditions and attempts |
| `content.put` `content.get` | content by id, in chunks |
| `key.list` `key.add` `key.revoke` `key.rotate` | owner sessions only |
| `seed.give` `seed.have` `seed.want` `seed.offer` `seed.ack` | seeding and reconcile between two booths |
| the home's operations at the gate | items, drafts, import, export, search, tasks, disclosure, programs, engines; under the session key |

B4. A program sees its own key's view and nothing else: the booth opens envelopes for a
    session with that session's reader only. A booth opened with a limited key serves at
    most that key's view.
B5. A guest without a key is served read-open addresses, and may `append` only under an
    open grant after `prove` with the root key of a genesis it presents.
B6. An engine is a program: it connects with a key, binds its namespace, and uses these
    ops. Rokh holds no engine's name, version, application id or path in code. The host
    reads them from an engine manifest given at start. Replacing an engine is replacing
    the manifest.
B7. Codes: `view_denied`, `key_revoked`, `vessel_full`, `vessel_corrupt`, `turn_lost`,
    `turn_unavailable`, `seed_refused`, `anchor_differs`, `ancestry_unproven`,
    `content_conflict`, `content_incomplete`.
B8. A booth that cannot prove an event's ancestry answers `ancestry_unproven` and records
    nothing (C8). A booth whose owner adapter is gone records nothing (C9).

## 6. Surface

- Three layers are shown and nothing else of the layout: **Star** is the rokh itself
  (anchor, system events, keys, seeds); **Planet** is the first address component;
  **Moon** is the second. Deeper components are listed inside their Moon. `rokh view DIR`.
- Commands: `init --size --slab --growth`, `grow`, `shrink`, `seed`, `reconcile`, `key
  add|list|show|revoke|rotate|passwd`, `grant --open`, `view`, `bring` (into the
  vessel), `daemon`. Each writing command takes `--attempt NAME`; the same attempt again returns the
  first result. This covers bring, grow, seed and rotation.
- One passphrase rule for every command: `--passphrase-file FILE` (`-` is standard input),
  then `ROKH_PASSPHRASE_FILE`, then `ROKH_PASSPHRASE`, then the terminal. One function.
- `rokh unshare --target` takes a full id or a short name of at least 8 hex digits that is
  unique among the live shares; the event records the full id.

## 7. The 0.9 format

The v1 format is fresh (goal 7.44). v1 does not read the 0.9 carrier or home format,
does not convert from it, and keeps no compatibility code for it. A folder in the 0.9
shape is answered with `not_a_vessel` and is never written.

## 8. What cannot be proven or promised

U1. That a vessel exists, its size, and when and how much it was written.
U2. Completeness. A roll back to an older whole generation and a hidden branch are not
    detectable without an earlier witness kept outside.
U3. With the mechanism of section 2, a copy during which more than R commits start. This
    is a gap against goal 7.1, not a limit of nature: see G1.
U4. Survival of a power cut on a medium that does not honour a flush. `recorded` means
    written, flushed and read back.
U5. Mutual exclusion between two machines on one synced folder. No committed generation
    is damaged; concurrent recordings may be lost. Two machines use two seeds.
U6. Unseeing. A revoked key opens what was sealed to it and, holding VK and the system
    reader, sees the shape and the system layer of any later copy of that vessel it
    obtains. Closing that needs a new vessel made by seed.
U7. In a restricted view: whether an ancestor whose body cannot be opened obeyed its own
    grant. Its lineage and its author are proven; its content is not (3.3).
U8. A host compromised while the vessel is open.
U9. That the holder of a key is a particular person; that an open-address writer is more
    than a key that signed a genesis.
U10. Exactly-once for an effect outside Rokh.
U11. Recovery of a lost owner passphrase. Out of the design, permanently.

### Open gaps, red until closed

G1. Live copy (goal 7.1: a copy of the folder at any moment, even in the middle of
    writing, opens to the last complete commit). The mechanism of section 2 proves this
    for a cut at any byte and for a copy during which no more than R = 3 commits start.
    It does not prove it for any number of commits. Counterexample: a copier reads the
    four head files at generation a, then reads the slabs slowly while a writer commits
    a+1 to a+4. Commit a+4 may reuse a slab that was live in a and freed in a+1. The
    copy then holds the heads of a−3 to a and a slab of a+4: no generation in it is
    whole and it does not open. Acceptance A2 stays red for the full clause whatever the
    bounded tests show. Closing it needs committed bytes that are never overwritten and
    a commit log that only grows; that is a change of section 2 and is the reviewer's to
    order.
G2. Two machines writing one synced folder (U5). No lock reaches across machines.
    Stated, not solved.
G3. Windows and Android at run time. Adapters may be built; nothing is run there on this
    host.
